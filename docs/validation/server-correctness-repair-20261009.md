## K 线修复

一分钟桶被墙上时钟关闭后，后到的有效成交以前会被直接丢弃。现在在三天去重保留期内接收新的有效成交，先持久化修订后的分钟桶，再发布 CLOSED 通知；SQL 失败保留 dirty 状态重试。不会用当前价格补造历史蜡烛。

分钟修订会从持久化 M1 重建相关高周期桶，查询范围有周期上界，周线最多 10080 分钟。普通新分钟仍增量合并。原有 rollup seen store 保存分钟成交笔数版本，重复或旧通知不再重复查 SQL；旧正数时间戳格式可就地读取并转换。三天去重记录过期后，活动周线的 lastMinute 仍防止旧分钟再次计入。

修订版本不能只用 lastSequence：一个事件时间更早、导出序号更高的成交，可能增加成交笔数而不改变收盘成交。SQL 使用已接受成交笔数的单调增长决定修订；测试覆盖这一情况以及缓存一致性。这里是追加成交修订语义，不是支持撤销历史成交。

已独立修复此前确认的 ETH 19:03、ETH 19:12、SOL 19:04（10-08 UTC）三根分钟线。修复使用此前完整捕获的已提交成交与当时编码，事务内核对旧值后更新，再发布三条修订通知。三个 REST 结果的 OHLC、量、笔数和首末成交全部复核通过。

f974fa21 部署后，独立消费者使用 `read_committed`、手工 assign、禁止自动提交，读取固定 offset 范围的 5298 条成交。BTC/ETH/SOL 各核对 02:32–02:51 UTC 的 20 根闭合 M1，共 **60 根全部一致**：OHLC、base/quote volume、tradeCount、first/last tradeId、first/last sequence。合约编码在核验前后相同。

03:03 UTC 额外观察确认成交导出仍落后约 194 秒，checkpoint 与 Core commit position 差约 8.5MB，不能把 Kafka 消费组低 lag 当作导出已实时。采样显示订单投影 SQL 等待，本轮继续增加 c79d572b 追赶合批修复：日志落后超过 64KiB 时，合批目标期限暂从 5ms 增至 100ms，接近实时后恢复 5ms；容量限制、完整命令边界、订单事务先于 Kafka 及 checkpoint 条件不变。用户部署 c79 后，独立 read_committed 消费者连续采样 5 分钟、21 次，最新成交最大事件年龄从第一笔采样的 3.51 秒到最后 0.788 秒；21 次最大值为 3.51 秒。03:29–03:33 UTC 三个合约另外 **15 根分钟线全部匹配**。checkpoint 约每 60 秒保存一次，其字节差不能替代实时成交事件年龄；前后还有用户其他服务的部署变化，因此不据此给出独立吞吐提升百分比。

## 资金费修复及真实历史恢复

调度先查询维护状态和 Core 结算进度，失败时停止本轮；已完成窗口不再重复写预测 FINAL。首次结算输入冻结于数据库，后续分页与重启沿用同一费率，避免中途预测更新导致同一窗口换费率。

实际历史取自独立 Archive replay 的 APPLIED 结果，导出包含真实支付明细、游标、Core log position 和结算时间。投影事务按产品线/合约/窗口加锁，页幂等写入；只有从 cursor=0 连通到完成且费率一致，才形成完成结算。重复、冲突、缺页和数据库失败不会把未完成窗口标为成功。导出 checkpoint 只在持久化成功后推进。

真实扣款仍由原 Core 资金费命令执行。新增 observer 只安装在独立回放实例；未修改实时撮合、资金费金额公式或账户状态。支付 projection 的 export_sequence 使用 Core log position，不与成交 sequence 混用。

## WebSocket 与资源工作量

真实浏览器曾确认交易页同时建立两个连接。现在同一 endpoint resolver、同一 token 的页面订阅共享物理连接，合并订阅集合，回调仍按产品线、频道、合约及周期隔离；accountState 只交给相应拥有者。新消费者补订快照，最后一个消费者释放时关闭连接。token 与 endpoint 不同的会话保持隔离。超过服务端 180 订阅上限才按现有机制拆连接。

自动发布后的真实页面连续 30 秒 **maxActive=1**，用户服务器更新后于 03:37 UTC 又完成一次同样的 30 秒核验，仍只有一个活动连接。认证 token 共享、重连、晚加入快照、引用计数、退订及 240 项订阅拆分由单元测试覆盖。此浏览器核验使用公开行情，未凭空创建登录凭据。

服务器公网 WSS 与本机环回 WS 对照各连续运行约 3601 秒，各一条连接、约 9.57 万条事件，只有测试结束时主动正常关闭（1000）；异常关闭、解析错误、盘口序号缺口、非法/交叉盘口、非法 K 线均为零。该窗口跨越部署，不能称为最终版本的一小时稳定运行测试。

本机 Chrome/Node 一小时分别出现 8/7 次异常关闭。Chrome Netlog 确认经过本机 SOCKS 代理，关闭时 TCP/SSL 读到 EOF，未收到 WebSocket close frame。精确故障跳点未确定；尝试禁用代理的浏览器仍经过 SOCKS，不能当作直连对照。没有据此修改服务器心跳协议或把网络原因写成已确认的服务器 bug。

## 资金费预测缓存的追加优化（240ccf4c，待用户部署）

用户重启后 03:28 的活动资金费缓存 lag 约 9.58 万，03:37 仍有 7172，不能与已退出 group 的历史 lag 混为一谈。该派生缓存从 earliest 恢复历史，每条监听成功后使用 RECORD 同步提交 offset，增加不必要的往返。不能简单跳到 latest：停机期间应结算的历史窗口仍要恢复。

改为保留原消费范围、逐条校验和缓存 sequence 规则，只把确认改为每个 poll 处理完成后的 BATCH。真实 Spring 监听容器配合 Kafka MockConsumer 和实际业务缓存，对两个永续产品各重建 1001 条记录，包含最后重放一条旧版本；原模式 1001 次 offset 提交，新模式三次（500、1000、1001），再次完整重放结果一致。没有增加缓存索引、线程、配置或资金命令。确认语义依据 [Spring Kafka 官方说明](https://docs.spring.io/spring-kafka/reference/kafka/receiving-messages/message-listener-container.html#committing-offsets)。这是提交调用次数验证，不是实际网络吞吐基准。

代码、中文 README 和测试已推送 **240ccf4c**；实际 lifecycle PID 2269882 的 class 仍含 RECORD、未含 BATCH，因此该项 **尚未部署，也未声称通过线上启动效果验证**。服务器部署由用户负责，本会话没有为该项重启服务。
