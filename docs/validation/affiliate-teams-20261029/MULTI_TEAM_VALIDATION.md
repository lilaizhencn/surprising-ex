# 多团队并发核算、结算与恢复验证

结论：本轮在 **1000 个六产品团队**及 **10000 个 SPOT 团队**上完成全量核算、结算与资金恢复验证，未发现跨团队记账、重复实际扣入款或资金差额。性能容量判定仍为**未通过正式门槛**：运行期间存在全系统换页和 CPU 限频，不能用这些耗时承诺生产 TPS。

本记录补充同目录 [Gateway 编译验证](README.md)，属于另一组实际执行的验证。工作区并行提交 `0ce0862f1` 保留了团队隔离、迟到费用补结和既有 Core 测试编译修复；本报告不改写该提交。大型运行的业务实现与该提交一致，后续标准 Maven 回归按当前主分支再次执行。

## 验证范围

- 使用真实 PostgreSQL，4 个独立 Spring 业务容器、4 个独立 Hikari 连接池，共享同一套表，8 个工作线程同时核算/准备/发送。没有以一个线程轮流调用来冒充多实例。
- 业务容器不等于 4 个完整 Gateway 网络进程；HTTP、Nacos、真实 Aeron 传输及 Archive WAL 压力不在大型运行中。费用是明确的测试夹具，经真实数据库和实际返佣业务代码处理，不称为本轮实际撮合产生的费用。
- 资金使用 6 个按产品隔离的真实确定性 Core 回放副本。每产品有固定所有者线程，所有资金请求经该线程执行；没有为了测试关闭 Core 所有者检查。首次夹具错误地跨线程调用 Core，已改正后重新运行，未将夹具问题归因于生产资金协议。
- 大型夹具全部团队都活跃，每队一名客户产生两笔费用，其余客户用于背景资料规模；没有验证所有客户同时交易。常规深度 1/3/6，另含一个 256 节点热点团队，客户数量和团队成员分开统计。币种使用 USDT/BTC 的整数最小单位，所有对账按产品/资产分别进行。
- 运行前锁定 [计划](plan.md)。只有当前 master 与本轮待提交代码，没有回跑旧提交或修改交易在线 Core。使用 HotSpot Corretto JDK 27、Maven 3.9.16、PostgreSQL 18.4。

## 为什么多团队仍然有界

数据是多棵独立团队树。每笔费用沿自己的直接邀请人与有效祖先路径查找顶层，佣金桶按产品、订单、顶层和规则版本隔离；分配只遍历这条路径，不遍历全部团队。没有为每个团队创建线程，也没有维护深链下平方规模的全量闭包表。

同产品核算仍由 PostgreSQL 产品锁串行保证幂等与累计舍入；不同产品可并行。多实例扩大的是任务竞争与故障接管能力，不承诺同产品核算随实例数线性加速。批次、完整路径行数、查询/事务期限、结算认领和查询并发均有上限。

多团队回归发现并修复两项问题：

1. 原来一个坏团队会使同产品整批回滚。现在可判定的历史关系异常先持久化隔离费用的完整身份与金额，再推进接收断点；健康费用继续。确认断点保持在最早未解决费用之前。修复后使用原身份、原发生时间核算，不改写为零、不截断分账。金融事实冲突与数据库错误仍回滚对应事务。
2. 一个产品先完成自动结算后，稍后投影到达的其他产品旧费用可能被延后一个周期。现在保存当前自动周期的费用截止时间；属于已关闭周期的迟到成熟费用可以补结，原下次周期不被提前。即使新旧费用共享同一用户/产品/资产组，准备结算也只选当前允许的截止时间内的行。

隔离默认每产品最多 10000 笔，最多 100000；每次恢复最多 16 笔（可配 1–64），失败默认延后 60 秒。隔离恢复与健康接收有独立事务/行数/时间预算。队列满时在尚未完整保存的费用前停止，形成明确背压；这不是无限容量或任意故障下完全隔离的承诺。

## 故障恢复方法

部分请求在真实 Core 已扣款或入账后持续丢回执，故意保留 UNKNOWN，不先假装成功。首轮所有正常费用/组准备完毕后，停止并关闭 4 个业务容器及连接池，对各 Core 生成实际 snapshot 并恢复，逐产品比较恢复前后全部组合状态。重新建立 4 个容器，按原结算单身份重试；只将测试时钟中的 `next_attempt_at` 提前，没有改变金额、端点、业务键或 PAID 状态。

首轮 Core snapshot 中受未完成转账影响的用户分别为 390、600、390 个。恢复后组合状态完整，全部 UNKNOWN 归零。结算单数量随核算与准备的交错时序变化，同一用户可能有多张合法前缀结算单；金额与实际扣入不能随此变化。

首次隔离回归在旧行为上失败；迟到成熟费回归也先得到 `expected 2 / actual 1`。修复后新增测试覆盖队列满、提交中断、乱序修复、不可变事实、权威来源冲突、原历史费率、损坏循环、12 个独立团队的不同顶层/下级比例，以及同组新旧成熟费用不提前支付。

大型入口为 Gateway 测试源码 `AffiliateTeamWorkload`。编译测试后在 `surprising-gateway/` 执行：

```sh
java --enable-native-access=ALL-UNNAMED --add-opens=java.base/jdk.internal.misc=ALL-UNNAMED \
 --add-exports=java.base/jdk.internal.misc=ALL-UNNAMED -Xms256m -Xmx2g \
 -cp 'target/test-classes:target/classes:<test-dependencies>' \
 com.surprising.affiliate.AffiliateTeamWorkload 1000 50 <result.json> 1200
# 万队同产品：末尾另加 SPOT，规模改成 10000 5
```

环境变量仍指向专用数据库。完整 `init.sql` 在本轮独立库执行成功；验证过程使用的 schema 与数据库均不承载生产资金。运行脚本、资源和精简命令输出见本目录归档。初版 runner 将结束时刻误记为 start_utc，第一轮时间字段在归档中保留说明并按 elapsed 近似还原，未伪造精确窗口。

已有库上线前停止全部 Gateway 写入，在事务中执行 `deployment/migrations/20261029-affiliate-team-isolation.sql`，再统一更新后端及后台。旧账号的周期截止时间不从历史猜测，首次新自动周期建立后启用对应补结边界；不会改写旧佣金或历史付款。没有执行生产发布。

最终独立库、QA/Vite、原始 JFR 和临时工具的清理状态见 [cleanup.json](cleanup.json)。正式容量仍需在无换页/限频环境按项目要求补真实单成员、单 Matcher、in-flight256 网络/Archive 链路及长稳验收。
