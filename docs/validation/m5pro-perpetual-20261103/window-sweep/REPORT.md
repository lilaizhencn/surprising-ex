# 扩大窗口诊断

结论：**性能验收无效，正确性通过**。本轮未观察到扩大窗口提升吞吐，但由于环境换出干扰且各档仅一轮，不能断言256最优或确定Core物理上限。保留生产有界窗口及默认值。

用户同意继续窗口诊断后执行。master 71a1210d2（仅文档变化，业务仍9088fc7cc），无源码改动。环境与前报告相同；每档新建真实单成员节点，1 matcher、2 Lane、256 symbols、100 users、1 worker/connection，买卖GTC各半，标记价更新，预热30秒、稳定60秒、单次重复；无profiler，种子9901，G1及堆配置相同。命令和全部日志见各场景子目录，sweep.py为实际编排。判定资金差0、终态一致、无未完成和业务失败；吞吐仅稳定窗口。

先固定Core256把客户端扩大为1024，再保持客户端1024把Core扩大为1024，最后两者扩大为2048；普通单和batch20分别测试。正式256基线仍见上一报告，扩窗不是替代基线。

系统swap占用从上轮末3.25MB增至13.5MB，未采集逐档换页时间与频率，无法排除各档污染，故整个扩窗性能比较按无效处理；系统未报告热或性能告警，不能据此证明无降频。普通单2048档及批量1024档存在区间吞吐波动，不得称稳定Core容量平台。相同100用户下同用户依赖/排队增加是待验证线索，不是已定位根因。

六档均退出0、capacity=PASS、fundsDiff=0、bookLevels=0、failures=0；排空unfinishedRequests=0，submitted=completed，撮合/账户/上下文队列0。未做快照恢复、强平ADL、长稳、精确B/op、GC/DirectBuffer、稳定窗口CPU/锁/缓存行采样，不能视为完整生产验收。

下一步应在环境隔离且记录换页增量后，以相同窗口重复基线与诊断并交错运行；另行一次只改用户规模或发压并行度，核对Owner窗口占用及同用户阻塞，避免将客户端排队误当Core算力上限。所有测试进程已退出；原始Archive保留target供复核，未修改或停止用户既有应用。
