# Core 快照与命令恢复的兼容边界

目标是让后端直接读取已发布的数据格式。正常升级不清空状态、不改写旧日志，不依赖停止脚本生成特定快照才能读取。新增可默认字段、Java 字段改名/调整声明顺序不能自动变成持久化格式破坏性变更。

## 恢复流程与状态权威

`AeronTradingClusterService.onStart` → `ClusterCoreSnapshotTransfer` → `SectionedCoreSnapshotRecovery` → `SectionedCoreSnapshotParser`：先验证封套、长度、CRC32C、产品线、提交水位、账户 Lane、资金哈希和 Matcher 配对，再构造候选 Runtime 并激活。随后 Aeron 按原始日志顺序、Cluster 时间和位置继续交给 Owner 执行。账户、订单和撮合都恢复已有事实；恢复快照不会重新执行历史成交或重新计算已结算余额。

权威数据仍是 Aeron 提交日志和完整快照。RocksDB 资金幂等索引、实时投影等不能代替它们。半成品、损坏或不支持的快照不能按空账户启动。快照、资金、撮合的原有一致性检查没有删除。

## 本次识别并修复的耦合

| 原有耦合 | 后端实现 |
| --- | --- |
| 交易状态 v35/v36 按固定位置连续写字段 | `TradingStateSnapshotCodec` 新写 v37，使用嵌套记录中的固定字段 ID 和长度；`TradingSnapshotV36Reader` 保留已发布 v35/v36 读取 |
| 枚举序号依赖 Java 声明顺序 | `SnapshotEnumCodes` 固定编号；业务/资金/实体哈希使用相同稳定编号；终态保留类型也使用显式编号 |
| 算法单、止盈止损快照复用接口二进制 Codec | 新格式独立映射每一个持久化字段；不调用接口 Codec 编解码这两类状态 |
| 待完成划转快照嵌入当前划转命令编码 | `CoreTransferSnapshotCodec` 新写 v2 固定字段；仍读 v1 及其原始命令 v1/v2 |
| 费率快照固定位置字段 | `CoreFeePolicySnapshotCodec` 新写 v2 固定字段，保留 v1 读取 |
| 划转命令新增显式收付款人后拒绝旧 v1 | 从已提交命令头/快照记录中的用户恢复原来的本人跨产品线划转语义；不从登录态、配置或当前账户猜测 |
| 同一资金请求换编码版本后指纹不同 | 不改写原指纹；重试比对仅认可本人划转 v1/v2 的等价编码；不同金额、账户、产品线、收款人仍冲突 |
| `Map.copyOf` 破坏费率与划转记录的稳定遍历顺序 | 恢复结果保留有序只读 Map，避免多条记录在不同 JVM 中得到不同业务哈希 |
| 增加划转用户字段改变旧快照业务哈希 | 先按明确识别的旧格式核验原哈希、资金和 Matcher，再补齐旧语义中的用户字段并更新内存 Matcher 配对哈希；原始快照不改写 |

`SnapshotFields` 只负责持久化边界的编号、长度、数字、文本和嵌套集合。没有反射序列化运行时对象、全局类型注册、每笔命令状态复制，也没有进入撮合/结算热路径。新增的历史读取器只读已发布格式，不是故障时绕过校验的兜底。

## 普通字段演进规则

1. 字段 ID 是持久化契约，同一记录内部永久唯一。已有 ID 不复用；改 Java 名称或声明顺序时，编码和解码继续使用原 ID。新字段分配新 ID，不给全部字段重新编号。
2. 新增可选字段时，在读取器中明确历史默认语义，例如标记价格记录的 `lastPriceTicks` 缺失为 0（旧格式没有最后成交价）；不能对金额、数量、用户、订单标识等关键字段统一补零。新业务集合可在读取器中明确映射为空，现有关键集合仍须存在。
3. 数字统一采用 64 位持久化值；读取为 `int` 时做范围检查。缩放单位、金额含义、正负号语义变化不属于普通改字段，必须显式转换并验证资金不变量。
4. 未识别字段按长度跳过；重复 ID、截断、错误长度、非法 UTF-8、缺失必填字段均拒绝。已删除的可选元数据可以不再读取，但其 ID 保留，不承诺把旧版无法理解的经济事实静默丢弃。
5. 交易记录中的最小读取器修订号独立于封套和字段格式版本。仅可选字段新增不抬高要求；新经济事实无法由旧读取器理解时提高最低修订号，让旧程序明确拒绝，而不是错误恢复。
6. 新字段的历史默认值必须与原业务哈希兼容。不能无条件向旧哈希追加一个 0，也不能通过更新历史样本的期望值掩盖变化。确实需要改变哈希语义时，仿照划转 v1：根据持久化格式选择原哈希算法，先验证原数据，再在恢复边界转换；资金哈希和撮合核验继续保留。
7. 状态转换的中间进度（风险扫描阶段、资金费/交割游标等）也是持久化语义，不可重新解释旧阶段编号。增加阶段须保留原编号与对应恢复行为。

## 命令重放不能只靠字段兼容

快照恢复已有事实；快照之后的命令仍由确定性执行器重放。因此，修改手续费算法、触发条件或订单裁决规则时，必须给该命令的执行语义明确版本，保留历史版本解码及执行含义，或在入日志前把需要冻结的裁决输入写入命令。不能用当前配置、当前时间、外部行情替换原始已提交输入。

现有命令各自的 payload 版本由 `TradingCommandCodec` 等协议 Codec 负责；普通 payload 新增字段不得随意提高共享 `CoreProtocol.SCHEMA_VERSION` 并删除旧版本读取。原始命令 ID/指纹继续用于去重，不通过重编码历史数据改变身份。

本次具体覆盖划转 v1/v2 的解码、后续命令恢复和重试，未声称可以自动适配任意未来交易规则。尤其在同一个已发布命令版本中直接修改执行语义，后端无法仅凭那些旧字节推断原来使用的规则；这属于禁止的发布方式。版本化输入和固定历史恢复测试是长期契约，不是要求每次维护部署脚本。

## 各层格式的边界

- 外层分片封套仍是 v26；新增普通业务字段不改变其节顺序/账户 Lane 拓扑。
- 交易状态读取 v35/v36/v37，写 v37。
- 费率状态读取 v1/v2，写 v2。
- 待完成划转读取 v1/v2，写 v2；v1 中划转命令读取原 v1/v2。
- Matcher 原生状态仍是 v8，撮合引擎模块字节未改。本次没有承诺跨任意 exchange-core 原生格式、分片拓扑或资金单位变更自动兼容；这些是单独评审、验证的重大变更。
- 已发布版本更早、缺少明确历史格式定义的数据，不通过猜测字节含义恢复。

## 验证与维护

`PublishedSnapshotRecoveryTest` 从仓库固定二进制样本读取历史快照，覆盖六产品线、资金哈希、重复入账防护、升级后再次保存/恢复。样本来自原发布版本，测试不使用当前写入器制造“旧数据”。

`SnapshotFieldEvolutionTest` 覆盖字段顺序变化、未知字段、历史默认值、关键字段缺失/类型错误、最低读取版本、重复字段、截断、UTF-8 和数值溢出。`CoreFundsIdempotencyTest` 覆盖 v1 划转作为快照后的命令重放、恢复后的 v2 重试、短期结果淘汰后的长期幂等，以及收款人篡改拒绝。

每次涉及持久化字段或业务执行语义时，必须保留历史样本，补新增版本样本和跨版本恢复测试；不能删除旧读取器或重生成旧样本使测试变绿。常规验证包括协议/Core 全量回归、直接依赖服务恢复测试和快照恢复 JMH/JFR；本次实测结果在交付记录中补充。

### 本轮验证记录（2026-10-01，HotSpot JDK 27）

- 首轮协议/Core 及依赖 API 回归：1179 项，0 失败、0 错误，2 项既有跳过。
- 追加历史划转快照、旧哈希核验、终态编号和多笔划转顺序后，定向回归 40 项通过；真实 `a8df45ae` 快照无需改写即可恢复和完成划转。
- JMH `LinearPerpetualCoreBenchmark.snapshotRecovery`：4 个账户 Lane、16 档深度，1×1 秒预热、2×1 秒测量、1 fork，新格式恢复 217.457 ms/op；JFR 记录 272 次分配采样、1 次年轻代 GC。旧包同规模短测 219.804 ms/op，但未带 JFR，不能据此宣称性能提升。这只是恢复路径烟测，不代表线上恢复时长或平台吞吐容量。
- 最终协议/Core、tools、realtime、gateway 及依赖回归：1961 项，0 失败、0 错误，51 项既有跳过（含需独立 PostgreSQL/线上环境的集成测试及两项 Core 禁用用例）；没有将这些跳过项算作已通过。追加真实旧版本多费率/多划转样本后，8 项历史恢复测试全部通过。
- 故障边界由现有 SectionedCoreSnapshotCodecTest 等覆盖：各节校验和、截断、节缺失、Lane 路由、版本不支持、快照围栏超时、异步失败，以及无效恢复不启动/泄漏运行线程。六产品线原生 Matcher、持仓、资金费/交割/行权和止盈止损/OCO 恢复随 Core 回归执行。
- 服务器实际数据升级验证将在部署后记录。
