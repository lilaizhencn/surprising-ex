状态：已实现，并追加[资金与深层关系稳定性专项](validation/affiliate-safety-20261028/README.md)。2026-10-29 已修复 Core 重构遗留的 Gateway 测试编译错误，并验证异常团队隔离与相关资金功能，见[本轮记录](validation/affiliate-teams-20261029/README.md)。原界面验收与历史限制见[验收记录](validation/affiliate-20261028/README.md)；本轮未重新验收界面。

## 范围与部署

在现有 Gateway 中新增 `com.surprising.affiliate`，按 controller → service → repository/client 分层；不新增独立部署服务。用户 Web、Flutter App 和交易运营后台联动。普通用户注册即获得邀请码与邀请返佣能力，存量用户首次使用时补建资料。

下单、撮合、保证金、手续费计算、快照和在线恢复不调用 Affiliate。返佣只消费已提交 Archive 回放导出的实际费用事实。公开行情、当前费率、成交额推算和 Valkey 余额均不能作为计佣来源。新增通用费用投影只位于独立回放/历史导出路径，不添加 KOL 字段到交易命令。

默认普通邀请比例与顶层 KOL 比例均为 20%（200000 ppm），后台可配置；默认每日结算已满 24 小时的应付佣金，支持人工触发。自动结算可按用户开启/关闭。配置变化只影响生效后的事实，不重算历史。

## 邀请与团队

1. 每个用户有一个不可预测的邀请码。分享链接携带邀请码，注册页面和 App 深链自动识别、展示并允许核对。输入不存在、过期或不能接受的邀请码须明确报错，不静默忽略。
2. 普通邀请无需开通 KOL；新用户注册时填写邀请码，或已有用户主动接受邀请后，建立唯一直接邀请关系。本人不能邀请本人，不能重复改绑或产生循环。
3. 邀请归属与团队合作分别记录。KOL 可向已邀请用户提出合作邀请，并约定下级分配比例；双方均须先由后台管理员开通 KOL，被邀请人明确接受后成为团队下级。接受合作邀请只建立合作关系，不授予 KOL 权限；普通账号不能通过合作链接或携码注册自行开通。未开通时应先普通注册，管理员开通后再接受合作邀请。平台停用不能通过新合作邀请绕过。
4. 团队使用父子合作关系表达，可持续向下扩展，不写死老板/管理/渠道等职级。成员可以拥有自己的推广链接和下级。节点的身份、管理权限与实际收益分别处理，不共享账号或密码。
5. 用户成为同一团队成员以后，其本人交易不再给团队上级产生邀请佣金；该成员拓展的外部用户产生的费用，仍按实际归属路径分配。生效前已产生的应付佣金不撤销。
6. 直属上级可调整直属下级未来分配比例；首次入队须下级接受。历史合作条款保留版本。不得移走别人的用户、把祖先设为下级，或跨分支越权操作。
7. 关闭 KOL 停止新的合作邀请与该团队新佣金分配，保留历史关系、明细与已确认应付款。普通邀请能力仍存在；不能以停用、再启用规避团队成员本人交易排除规则。

## 计佣与逐级分配

每笔正交易手续费按来源用户找到直接邀请人，再沿该邀请人的有效团队合作路径确定顶层。平台只决定顶层总预算；下级分配比例以其上级在该来源分支获得的佣金为基数。

例：外部用户产生 100 USDT 合格费用，顶层比例 20%，顶层给管理 60%，管理给渠道 50%。顶层获得额度 20、留存 8；管理获得额度 12、留存 6；渠道获得并留存 6。最终应付合计 20。另一个渠道的比例作用于其自己的来源分支，不把所有兄弟节点比例相加。若将来添加同一笔费用多人共同分配，必须另外约束同池分配合计不超过 100%；本次不添加该扩展。

采用整数最小单位和 ppm，以 BigInteger 中间运算避免乘法溢出。顶层按产品、订单、顶层、平台配置版本和比例累计正费用计算增量；订单的收费资产由权威费用事实固定。每条合作条款按产品、订单、资产、条款版本持久化累计收到额度，用 `floor((历史收到 + 本次收到) × 下级比例) − floor(历史收到 × 下级比例)` 计算本次下拨，而不是对每笔碎片单独取整。未分出的整数余数暂留本层，后续累计可触发最小单位下拨，任何时点都不会超出本次实际收到额度。例如同一订单 100 次各 1 单位费用，平台 20%、下级 60%、再下级 50%，最终留存为 8 / 6 / 6，总计 20。所有资产独立核算，不自动换币；负费率 maker rebate 不计入正收费，不计资金费、强平罚金、提现费。

计佣明细保留来源事实、产品线、用户、订单、费用资产、实际费用、发生时间、邀请人、合作条款与平台费率版本、获得额度、下级分配和留存。重复导出与重试不能多计。同来源不同金额必须报错。未获足够费用事实或来源不可读时报告积压，不把未知当作零。

可明确识别的关系异常保存到 `affiliate_deferred_fees`，同产品的其他团队继续核算。
隔离费用身份不可修改或删除，只有产生一致核算凭证后才能标记解决；身份冲突或数据库错误仍整体回滚。
`readClusterPosition/readOrderId` 表示已接收事实，原 `clusterPosition/orderId` 表示已确认断点，
不得跨越最早未解决费用。后台来源响应另提供 `deferredCount/oldestDeferredAt` 及错误原因。
修复后按费用原发生时间使用历史关系和费率补算，不重置身份、不重复付款。

每产品默认最多保留 10000 笔未解决费用（`max-deferred-fees`），重试每批最多 16 笔
（`deferred-batch-size`），失败后等待 60 秒（`deferred-retry-seconds`）；配置前缀均为
`surprising.affiliate`。队列满时在尚未保存的费用之前停止接收，不跳过事实；
正常接收与修复各自使用独立事务及行数、时间预算。自动结算保留周期费用截止时间，
迟到的成熟费用可以补结，下一周期费用仍等待原结算时间。

## 贡献可见性

用户可查看本人邀请，KOL 上级可逐层下钻本团队，暂停期间仍可查询历史。普通邀请列表展示该用户对本级的贡献，不开放其独立下游团队的财务查询。分别显示直接邀请人数、团队去重人数、有效交易人数、直接贡献、团队贡献、获得额度、下级分配、本人留存、待结算和已到账。金额按产品线与资产列示，不直接相加不同资产。团队合计不重复累计祖先与后代的小计。修改管理员或比例不能搬移历史贡献。

首次实现使用合作成员本人的认证账户作为其收益归属与管理身份，以合作树表达团队；不新增企业法人、多人共享资金账户、任意岗位系统或工资分配框架。后续多人协作应通过明确成员授权扩展，不能通过共享账户实现。

## 资金与恢复

佣金账本代表应付款，不能直接成为保证金。后台为每条产品线指定已按现有流程备资的预算账户；未配置、余额不足或账户不可用时保留待结算并显示原因。禁止直接 UPDATE 用户余额，禁止通过普通返佣调用无来源的余额调整。

按用户、产品线、资产将成熟佣金聚合成不可变结算单，使用既有 ProductTransferCoordinator 从预算账户划转。先持久化结算身份与明细，再调用资金接口。结算单保存固定的付款人、收款人、金额、资产、产品与幂等键；超时或结果未知保持在途，使用原身份向前恢复，不能换键重发或凭超时退款。只有明确成功才标记到账。停用自动结算不取消已经承诺的在途资金。

多实例使用数据库任务认领、唯一约束与事务保证一致性。关系/配置变更持有独占业务锁，核算持有共享配置锁与本产品锁；同产品串行，不同产品能够独立推进。费用、全部层级分配、累计舍入桶、结算工作索引和消费游标在同一数据库事务提交。资金调用在事务外，逐张认领，不提前占用后续结算单租约；每次认领生成新 token，迟到回写必须匹配当前 token。租约过期时仍可能有并发网络请求，资金防重依靠跨尝试不变的原 Core 业务身份，不能把认领 token 当作新的付款身份。调用资金前再次验证结算金额等于关联应付，账目异常时阻止调用。历史重算与发放不得占满下单线程。

对账按产品线、资产分别验证：平台佣金池等于各层留存之和；已确认应付等于未结算加结算在途加已到账。后台配置写入要求权限、原因与审计，手动结算与重试记录操作者和对应动作。任何人工冲正须单独流水，不改写原明细。

## 页面与接口

- 用户 `/affiliate`：邀请码/链接、接受邀请、邀请用户列表、团队逐层查看、贡献、佣金、结算记录。KOL 显示合作邀请、直属下级比例设置；未开通只显示基础邀请返佣，不显示 KOL 标题、开通提示、合作路径、团队身份、比例或合作邀请列表。好友列表显示其为当前用户产生的已确认返佣，按产品/币种分别列示；到账以结算记录为准。
- 注册 `/auth/register?invite=...`：自动填写并核对普通邀请码；合作码不能用于普通注册，不展示其团队比例。已有且获批账户进入接受合作邀请页面。
- App：账户页入口、注册邀请码、邀请深链接收、团队与收益页面；覆盖键盘、窄屏、安全区、错误重试和返回。
- 运营后台：默认比例、结算周期、KOL 开停、个人自动结算、产品预算账户、来源积压、手动结算及失败重试。所有金额和状态来自真实接口。

## 持久化与运行边界

- 部署前，在 Gateway 和 Realtime 历史导出使用的 PostgreSQL 执行 `deployment/migrations/20261028-affiliate.sql` 、`deployment/migrations/20261028-committed-trade-fees.sql` 与 `deployment/migrations/20261028-affiliate-safety.sql`；新库 `init.sql` 已包含三者。脚本不修改 Core 的余额或交易状态。先迁移，再更新导出服务和 Gateway，最后更新三端。
- 已有返佣库还需停止所有 Gateway 写入后执行 `deployment/migrations/20261029-affiliate-team-isolation.sql`，再启动新版 Gateway；新库 `init.sql` 已包含此迁移。
- `core_trade_fee_progress` 保存各订单权威累计费用基线；`core_trade_fee_facts` 保存增量。导出启动先读取现有快照的保留订单并建立基线；新命令与订单历史在同一 PostgreSQL 事务提交，失败整体回滚。不会把上线前的累计手续费一次性计佣。
- 事实身份为 `(product_line, order_id, cluster_position)`。消费者使用 `(cluster_position, order_id)` 游标，不使用数据库自增号作为业务顺序；同一撮合命令两侧订单都能被读取。日志需按产品线单一权威顺序导出，禁止从不同生产集群向同一产品历史写入。
- Gateway 专用调度器两个固定任务分别处理核算与资金 I/O，不为成员或费用创建线程。核算每 250ms 轮转一个就绪产品，每批最多 64 条事实、8192 行完整分配，处理达到约 250ms 后在完整费用边界让出；无新增数据休眠 10 秒，异常保留游标并按 2–60 秒退避。结算每秒调度，单次准备最多 16 组、每组 256 行，单次资金发送最多 10 次且逐张认领。大额超过 int64 的应付按可表示的前缀拆批。租约默认 120 秒，未知结果按 10–300 秒退避；重试始终使用原 Core 幂等身份。250ms 是完整步骤之间的让出目标，不是强制打断一笔事务或资金调用；Affiliate SQL 默认超时 2 秒，写事务默认 5 秒。后台来源面板展示检查时间、日志游标和错误；生产吞吐与长期积压需要独立容量验收。
- `affiliate_settings`、`affiliate_profile_history`、`affiliate_team_terms` 保留生效历史；当前资料用于页面，费用发生时间对应历史决定核算。`affiliate_fee_receipts`、`affiliate_commissions` 与累计舍入桶负责去重、分配与来源审计。
- 已明确拒绝的结算可人工生成一张替代单，原单持久化 `replacement_id`，连续点击或多实例重试不会多生成；迟到的未知响应不能覆盖已到账或明确拒绝的终态。未知结果不能创建替代身份。
- 新增读权限 `admin.affiliate.read` 和写权限 `admin.affiliate.write`，迁移授予既有 ADMIN 角色；后台写入必须提供原因，手动结算/重试也记录操作者和原始结算身份。合作成员只能写直属下级比例，上级只能查询自己的合作后代，不能修改更深层条款。
- 公开分享为 Web 链接；Web 页面提供 `surprising://affiliate?invite=...` 打开 App。Android 注册 affiliate intent filter；iOS 复用已有 surprising scheme。未配置生产域名关联文件，因此不宣称 HTTPS Universal Links/App Links 可直接唤起原生 App。

## 主要 HTTP 契约

所有用户身份和整数金额使用十进制字符串，比例为 0–1000000 ppm；用户界面通过权威资产 scale 精确显示，缺精度明确报错。历史记录与结算状态不通过前端推算。

## 深层关系与运行保护

- 关系存储采用唯一直接邀请人和父子合作条款，避免闭包表在深链下产生平方级行数。绑定在独占配置锁内检查祖先，拒绝自邀、改绑和环。历史条款保留版本。
- 核算路径一次有界递归 SQL 快照读取，SQL 用 `UNION` 去重终止损坏的环；Java 使用 `HashSet` + 迭代验证唯一节点、连续路径和根，不递归调用 Java 栈。默认最多返回 4097 行检测 4096 节点上限，超过上限或发现重叠历史不写任何部分佣金，后台将完整费用持久化隔离，健康团队继续；确认断点不会越过未解决费用。单笔核算的应用计算和必要账本行数为 O(路径深度)，不遍历兄弟团队；团队人数统计按需遍历去重，有查询超时和并发门限。
- `affiliate_settlement_groups` 是可重建的待处理索引，金额权威始终是不可变佣金明细。仅对有待处理数据的用户/产品/资产扫描成熟前缀，自动结算只调整本批用户下次时间；不会每秒更新全体用户。缺预算或账户不可用按组阻塞并延后检查，不拖住其他产品。
- `surprising.affiliate` 配置集中定义路径、批量、行数、时间、租约及查询并发门限，启动校验必须允许一条完整路径。默认最多 4 个昂贵团队查询并发；繁忙、超时或损坏历史返回既有 `message` 错误结构与 HTTP 503，页面可刷新恢复。此门限按 Gateway 实例生效，增加实例需同时核算数据库容量。
- 安全上限是资源保护，不是承诺物理无限层级。上万成员不等于上万层；超过单笔路径容量时隔离该费用等待核查；隔离队列满、金融来源冲突或数据库故障时对相应处理施加背压或回滚，不通过提高上限掩盖坏关系。默认可配置到 16384 个节点，但本轮实际验证到 4096，不能宣称更深容量已经通过。
- 上线前停止所有 Gateway 返佣写入，用事务应用安全迁移，再启动统一版本的 Gateway。迁移回填旧明细的索引字段、待结算组及各条款历史收到额度；不改历史分配金额，不自动补付旧版碎片舍入差额。旧版下级少分的额度已留在上级，同池合计仍守恒，历史更正须核查并使用独立授权更正流水，不能直接再次补发。

具体配置、对账查询、故障恢复、实测数据及未测范围见[稳定性专项记录](validation/affiliate-safety-20261028/README.md)。

## 多团队验证与来源进度

团队按多个顶层组成森林，单费用只走实际归属路径。`readClusterPosition/readOrderId` 为完整持久化接收断点，原 `clusterPosition/orderId` 为不跨未解决费用的连续确认断点。后台展示 `deferredCount` 与 `oldestDeferredAt`，不能把接收进度等同全部核算完成。无效/缺失进度数据报错，不补成零。

已验证 1000 队六产品和 10000 队同一产品、多业务容器竞争、资金原身份恢复；具体数据、日期/调度语义、换页限制与未测范围见[多团队补充报告](validation/affiliate-teams-20261029/MULTI_TEAM_VALIDATION.md)。用户 Web/App 契约未变化，运营后台联动来源进度字段。


## 管理员开通前的前端边界（2026-10-29）

Web 与 App 都以当前登录人本人 `/me` 的 `profile.kolEnabled` 为开关，不以正在查看的成员是否开通决定权限。刷新时重新读取本人状态；关闭后退出成员分支、清除合作草稿，恢复基础邀请页。资料读取失败清除旧 KOL 页面，恢复后可重试。普通用户的模块入口统一为“邀请返佣”。

后端合作邀请接受流程已移除自动开通权限的写入；未开通时拒绝，并保持邀请未使用、没有部分绑定或权限变更。管理员开通后可沿用原邀请接受，重复接受仍幂等；普通邀请无需 KOL。历史佣金、资金身份和已有已确认应付不重算。本轮没有修改交易在线链路。

若环境曾运行旧版“接受合作即自动开通”，已有 `kol_enabled=true` 不会被本轮按猜测批量撤销；发布前管理员应复核旧账号并通过后台确认保留或关闭。可用最新 `affiliate_profile_history` 中 `actor_id=user_id` 且 reason 为 `接受团队合作并继承分支管理权限` 的记录定位待复核账号；这只是核查线索，不自动更改历史权限或资金。

权限、UI 契约与设备实测边界见[开通边界验证](validation/affiliate-access-20261029/README.md)。
