# 高并发与资金安全改造执行计划

## 1. 目标和执行原则

本计划以统一的用户分区事实流为主线，四条业务线共用顺序、幂等、快照和恢复边界；现货、永续、交割和期权只实现各自的结算规则。具体实现使用 `SPOT`、`LINEAR_PERPETUAL`、`INVERSE_PERPETUAL`、`LINEAR_DELIVERY`、`INVERSE_DELIVERY` 和 `OPTION` 六个隔离的 `ProductLine` 值。

核心目标不是单纯减少 SQL，而是让每类可变业务事实只有一个写者，并且在重试、重启、重平衡和多节点竞争下仍保持资金守恒：

- 账户命令按 `productLine:userId` 串行，余额、冻结、保证金、持仓、持仓模式、未平仓量和账本由账户模块统一变更。
- 订单、撮合、Funding、Risk、Liquidation、ADL、Insurance 只能发送账户命令，不能直接写账户事实表。
- Instrument、费率、账户状态、持仓、未平仓量和行情由内部 RPC 做一次初始化，再由产品线隔离的 Kafka 增量更新各模块 JVM 快照。
- 快照未就绪、版本间隙、事件过期、产品线或 Kafka key 不匹配时必须拒绝或等待，不能回查数据库并猜测，也不能把缺失状态当成零。
- PostgreSQL、Redis 和 JVM 快照的职责必须明确：用户分区 WAL/RocksDB 是账户在线事实源，其他存储只承担事件投影、恢复、查询和审计。

## 2. 当前永续基线和已发现问题

当前订单和账户资金热路径已经由用户分区 Kafka 命令、WAL/RocksDB reducer 和 JVM 快照裁决；`account_commands`、订单表、持仓表和其他 Repository 只保留异步投影、启动恢复、查询和审计职责。快照未就绪或事件版本冲突时仍然失败关闭，不能回查数据库。

本轮先修复了三个恢复一致性问题：

1. 账户快照 RPC 只用于用户分区启动初始化；在线余额、持仓、保证金、订单冻结和持仓模式来自本地 WAL/RocksDB 快照，数据库事务不参与热路径裁决。
2. JVM 账户快照对同一 `accountRevision` 的重复 RPC/Kafka 事件保持幂等，不再用新的 `eventId` 或时间覆盖已有状态。
3. 普通异步下单不再把读取到的异步账户修订号作为强栅栏；账户命令仍按用户 Kafka key 串行，最终资金裁决仍由账户事务的原子预占完成。只有显式批次依赖链保留命令依赖关系，避免做市商并发下单因修订号已被前一条命令推进而全部误拒。

### 2.1 当前代码审计结论（2026-08-02 复核）

本次改造不能只按模块名称删除 Repository，必须先区分“事实写入”“恢复读取”“在线投影”三类路径。当前代码复核结果如下：

| 链路 | 当前唯一事实源 | 在线读取 | 仍需处理的风险 |
| --- | --- | --- | --- |
| 账户余额、冻结、持仓、账本 | 用户分区 WAL/RocksDB reducer | 账户 JVM 快照 | 只能由账户命令修改；数据库只异步投影和审计 |
| 下单规则、费率、Instrument、未平仓量 | Instrument/费率/账户状态/未平仓量 JVM 快照 | 订单模块本地无锁读取 | 快照初始化、修订间隙和同修订冲突必须 fail-closed，禁止热路径回查数据库 |
| 下单持仓模式、减仓容量、保证金模式冲突 | 账户状态快照 + 订单/触发单事件投影 | 各产品线 JVM 快照 | 事件缺失、修订间隙或同修订冲突时失败关闭 |
| 撮合订单簿、自成交、Instrument 版本 | 撮合 JVM/Chronicle 恢复快照 | symbol 分区单线程顺序 | 恢复完成前不得消费新命令；事件重放必须不重复成交 |
| Trigger 候选 | Trigger JVM 本地索引 + Redis 跨节点索引 | 本地优先、数据库精确 claim | Redis 不可用时不能把缺失候选当空；claim 必须保持跨节点唯一 |
| 风控和强平 | 风控 JVM 风险组快照，账户命令落账 | 本地计算，数据库仅恢复/审计 | 风险快照过期、标记价过期、候选版本落后必须拒绝执行 |
| WebSocket | Kafka 事件 + JVM 有界环形队列 | 批量 fanout、慢连接背压 | 队列满、断线重连和事件乱序不能影响账户事实 |

当前仍保留的数据库路径只允许用于异步投影、启动恢复、后台审计和跨节点协调；任何新增的订单或账户热路径 SQL 都属于回退逻辑，必须拒绝合入。其他模块的候选租约和投影删除需单独完成版本栅栏验证。

本轮特别纳入同修订事件冲突审计：账户、订单、费率和持仓缓存不能因为 `revision` 相同就用不同 payload 覆盖已有状态。相同修订的相同 payload 只能幂等忽略；相同修订但 payload 不同必须让该产品线快照进入不可用状态并触发重建。

## 3. 永续执行顺序

### 阶段一：账户命令幂等和恢复

审计 `AccountCommandRepository`、`AccountUserStateCommandWorker`、WAL/结果库和结果消费者，补齐以下测试：

- 相同 `commandId`、相同载荷重复投递只能产生一次余额/持仓变更和一次终态。
- 相同 `commandId` 但载荷、用户、产品线、依赖或来源不同必须拒绝，不能覆盖原命令。
- 依赖等待、依赖拒绝、依赖成功重放和子命令重试都必须可恢复。
- 批次中任意一条出现不可恢复异常时整个数据库事务回滚，不能只提交前面的用户。
- 进程在注册、业务变更、终态更新、Outbox 发布四个位置分别中断后，重启和 Kafka 重放均不重复扣款。
- 结果消费者重复、乱序和跨产品线消息不得改变订单状态。

验收指标：命令终态唯一、账户账本流水唯一、Outbox `pending=0`、重复重放无新增流水，且资金逐项守恒。

### 阶段二：账户状态 JVM 快照影子对账

账户事件必须携带 `productLine`、`userId`、`accountRevision`、`eventId`、`commandId`、`traceId` 和前置修订号。订单、风险、强平分别使用自己的缓存和消费组，通过 RPC 初始化缺失用户，Kafka 只做增量更新。

影子对账逐项比较：可用余额、冻结余额、订单保证金、逐仓保证金、仓位数量、开仓价、已实现盈亏、手续费、资金费、持仓模式和未平仓量。任何差异都保留命令、事件、修订号和时间上下文，不自动修正资金。

### 阶段三：下单、撮合和结算并发栅栏

- 下单只读取 JVM 的 Instrument、费率、账户、持仓模式、未成交订单和未平仓量快照；快照不存在或版本落后直接拒单。
- 订单预占命令携带 `expectedAccountRevision` 和依赖命令 ID，账户单写者用版本条件原子拒绝旧预占。
- 同一用户批量下单沿用连续账户修订号；撤单、成交释放和部分成交释放必须使用同一订单预占事实。
- 撮合按 symbol 单分区顺序处理，成交事件以唯一 `tradeId`/`commandId` 发布；撮合重启先恢复订单簿，再消费当前 offset。
- 结算只处理账户命令，成交、手续费、资金费和强平费用均以命令 ID 幂等。

### 阶段四：行情、风险和强平

- 标记价、指数价和 K 线启动先初始化最新快照，再消费增量；按序列号和最大年龄拒绝旧价。
- 风险组只使用本地 JVM 快照计算，Redis 只用于跨节点租约、索引和恢复投影；风险状态缺失时 fail-closed。
- 强平候选带 `positionRevision`、`riskRevision`、行情序列和预期数量；账户单写者再次校验版本，旧候选只能取消，不能强平。
- Liquidation、ADL、Insurance 和 Funding 的重试只重放命令，不重复写账户事实。

### 阶段五：故障注入和多节点

永续必须逐项执行：

1. Instrument 先启动，其他 Provider 再启动；启动时验证所有 JVM 快照 ready。
2. 两个账户节点使用同一产品线消费组并发提交同一用户的重复下单、撤单和成交命令。
3. 在账户命令注册、结算、Outbox 发布、撮合订单簿恢复和强平执行期间发送 `SIGKILL`，随后重启并等待 Kafka 重放。
4. Redis 清空、Kafka 重平衡、单个消费者暂停、数据库只读/短暂不可用，验证交易不会把缺失状态当零。
5. 对同一用户并发开仓、部分成交、主动平仓和强平，检查订单终态、持仓、冻结、手续费、资金费和保险基金。
6. 运行 20 用户真实流程，再运行 5000 用户压测；最后等待所有 Kafka lag 和 Outbox pending 归零后才记录通过。

## 4. 资金和唯一性验收表

每个测试批次必须保存以下结果：

| 检查项 | 通过条件 |
| --- | --- |
| 余额守恒 | 期初 + 调整 + 盈亏 - 手续费 + 资金费 - 强平费用 + 其他结算 = 期末 |
| 订单冻结 | 预占、成交消费、部分释放、撤单释放之和与订单终态一致 |
| 持仓 | 数量、保证金、开仓价、已实现盈亏与成交事件逐笔一致 |
| 命令幂等 | 同一命令和事件重复投递不新增资金流水 |
| 版本 | 账户、持仓、风险和行情版本只递增，间隙或回退不参与资金判断 |
| 产品线隔离 | Topic、key、consumer group、账户类型和 instrument 不跨线 |
| 恢复 | 重启前后订单、冻结、持仓、账本和快照修订号一致 |
| 延迟 | Kafka lag、Outbox pending 和最老年龄在业务完成后归零 |

## 5. 四条产品线复制门槛

永续阶段一至五全部通过并提交稳定报告后，按下列顺序复制：

1. `SPOT`：先验证买卖资产冻结、成交扣减和撤单解冻，再验证公共行情和 WebSocket。
2. `LINEAR_DELIVERY`：在通用命令链上增加到期结算、持仓归零和交割流水，禁止复用永续资金费逻辑。
3. `OPTION`：增加权利金、行权、到期失效和买卖方权益边界，账户类型和 Topic 独立。

每条线都必须重新启动 Instrument、运行同一套重复命令/重启/多节点故障演练，并生成自己的资金对账报告。任何一条线失败都只回滚该产品线的消费/投影版本，不得让另一条线进入双写事实源。

### 历史流程记录（2026-08-02）

以下内容是旧数据库事实路径下的历史演练记录，不能作为当前用户分区 WAL/RocksDB 方案已经完成四条线生产验收的证明。当前重新验收时必须以本地事实流、快照 ready、Kafka lag、结果库和逐项资金守恒为准，不能沿用旧报告中对交割/期权生命周期的完成结论。

- `LINEAR_PERPETUAL`：重复下单、账户 `SIGKILL` 重启恢复、Funding、强平和资金对账通过。
- `SPOT`：买卖资产冻结、成交扣减、撤单解冻、重复下单、账户 `SIGKILL` 重启恢复和资金对账通过；虽然没有衍生品持仓平仓阶段，余额、冻结和现货预占仍按同一重启门槛验收。
- `LINEAR_DELIVERY`：重复下单、账户 `SIGKILL` 重启恢复、强平、到期结算和资金对账通过。
- `OPTION`：重复下单、账户 `SIGKILL` 重启恢复、强平、行权/到期生命周期和资金对账通过。

旧报告中的四条线资金对账和 Outbox 数字只反映当时的数据库实现；迁移后需重新执行，不能把数据库投影清空误认为事实流已完成。

本轮还验证了三处真实故障修复或测试护栏：风险快照在 Redis 恰好过期的读写窗口内改用本地 JVM 快照继续完成版本化替换，避免把 Kafka 分区处理阻塞在数据库回退上；行情刷新器持续消费最新消息，生命周期测试使用 `MAX(sequence)+1` 生成单调序列，避免新标记价被历史序列误判为过期；首次现货重建数据库但未删除共享账户 Topic 时，消费者按 `earliest` 重放旧释放命令并正确阻断（缺少预占），随后用清理共享 Topic 的正确测试前置条件复验通过。风险 Provider 变更后同步重建包含它的宿主 fat JAR，防止部署产物继续运行旧类。

在真实并发压测中又发现并修复了一个幂等安全缺陷：订单、算法单和触发单原先只按 `client*Id` 找到旧记录就直接返回，未比较重试请求的业务参数，可能把同一个幂等键误当成另一笔订单。现在三类 Service 在重放和数据库唯一键冲突两条路径都比较完整的业务意图；用户、产品线、交易对、方向、类型、价格、数量、有效期、保证金/持仓模式、只减仓、只做 Maker 等不一致会明确拒绝。修复提交为 `db6b2e9b`，并分别增加了单元测试。

旧日志路径仅供问题追溯，不代表当前实现已开放交割价结算或期权行权。交割和期权必须在各自 reducer、结算价不可变事件和资金对账测试完成后重新记录。

## 6. 允许关闭旧路径的条件

只有同时满足以下条件，才能关闭永续实时数据库持仓查询、强平 JOIN/行锁或其他高频回退：

- 连续压测和真实业务流程无资金差异；
- 重复、乱序、重启、SIGKILL、Kafka 重平衡和 Redis 清空演练全部通过；
- JVM 快照初始化、事件追赶和版本间隙均有明确 ready/fail-closed 指标；
- 两节点失去租约后旧节点不能继续发布账户事件；
- PostgreSQL 投影、Redis 投影和 WebSocket 延迟不影响账户事实；
- 保留只读审计和可回滚的投影版本，禁止恢复为两个可写事实源。

## 7. 分步执行清单与交付门槛

每一步都按“代码修改 → 单元/模块测试 → 单产品线真实流程 → 资金核对 → 故障复盘 → 提交”的顺序完成；未通过当前步骤不得继续删除下一层数据库路径。

### 第一步：缓存事件一致性和幂等

1. 检查 `PerpetualAccountStateSnapshotCache`、`OrderMarginSnapshotCache`、`FeeScheduleSnapshotCache`、Instrument 和未平仓量缓存的同修订行为。
2. 为重复事件、同修订冲突、乱序事件、产品线错配、快照重建中断补测试。
3. 消费者遇到冲突或修订间隙时停止当前分区处理，标记对应产品线快照不可用，不回查数据库猜测。

交付门槛：重复消息不产生第二次预占/结算；冲突消息不能覆盖旧状态；快照未 ready 时下单、减仓、风控和强平全部 fail-closed。

### 第二步：下单与账户命令版本栅栏

1. 将订单预占、撤单释放、成交消费、资金费和强平命令统一纳入 `productLine:userId` 的账户修订链。
2. 对同一用户并发开仓、平仓、撤单、模式切换和重复命令做双节点测试，验证命令顺序、依赖关系和终态唯一。
3. 在保留数据库事务锁的情况下先完成影子对账；只有影子对账连续稳定后，才评估用用户分区顺序替换高频数据库锁。

交付门槛：任何一次重试、进程中断或 Kafka 重平衡都不能多扣、少扣或重复释放资金。

### 第三步：撮合、Trigger、未成交订单和持仓模式

1. 验证撮合订单簿恢复、保护索引和 outbox 的事件顺序，覆盖重复 PLACE/CANCEL、部分成交、跨版本 Instrument 和自成交。
2. Trigger 使用本地索引发现候选、数据库单表条件 claim 保证唯一执行；Redis/本地索引不可用时必须显式降级为暂停，而不是空结果。
3. 统一普通订单、触发单、算法单和账户状态事件的本地容量索引，验证 `CROSS/ISOLATED`、`NET/HEDGE` 和只减仓容量不会混用。

### 第四步：行情、风险、强平、ADL、保险基金和 WebSocket

1. 标记价/指数价按序列、时间窗和重启最新消息初始化；过期价格不得进入风险和强平计算。
2. 风险、强平、ADL、保险基金只发送幂等账户命令，候选携带持仓/风险/行情版本并在账户侧二次校验。
3. WebSocket 使用有界队列、批量发送和断线重建，任何背压只影响推送，不阻塞 Kafka 和账户事实。

### 第五步：四条产品线生产模拟验收

按 `SPOT → LINEAR_PERPETUAL → LINEAR_DELIVERY → OPTION` 顺序逐线执行，每条线都先启动 Instrument，并单独保存日志、Kafka lag、快照 ready、Outbox、资金核对和故障时间线。每条线至少执行一次双节点重复命令、账户 SIGKILL、撮合恢复、Redis 清空、Kafka 重平衡和数据库短暂只读演练；所有业务线通过同一门槛后才允许关闭旧路径。
