# C2C 商家、买家与卖家本地业务验收

2026-10-20 至 2026-10-21，本轮本地启动 PostgreSQL 专用数据库、Kafka、Redis、SPOT FUSED Core、realtime、maker 和 Gateway，使用实际注册登录的商家、买家、卖家及两名管理员完成业务。资金通过已审批的账户调整 API 注入，再由真实 Core 划转；没有通过 SQL 改写钱包余额。KYC、验证码、价格输入和站外法币付款为隔离测试数据，没有调用银行付款或钱包服务。完整证据见 [验收记录](validation/c2c-business-live-20261020.json)。

## 实际业务入口

用户 Web 的 `src/features/c2c/C2cTradingPage.tsx`、Flutter 的 `lib/src/c2c_trading_page.dart` 提供自选买卖、报价、实名收款账户、商家申请、质押、广告、订单、付款确认、放币、取消与申诉；订单直接进入现有聊天页。管理端 `src/C2cBusinessPage.tsx` 提供经营配置、内部账户零金额初始化、商家与质押规则、收款审核、广告管理、申诉裁决及订单会话。后台敏感操作继续使用交易权限、审计与不同管理员审批。

买卖方向切换时，Web 仅展示当前方向和市场的广告，清除原报价；Flutter 清空旧列表并丢弃过时的查询响应。订单详情优先展示，避免被历史订单挤到小屏下方。金额用十进制字符串和最小单位计算、格式化，避免浮点舍入。

## 质押的资金边界

先执行 `deployment/migrations/20261020-c2c-merchant-bond.sql`；新建数据库的 `init.sql` 已包含同一结构。运营在后台配置正数质押币种与金额，未配置时无法质押或通过商家审核。测试策略为 100 USDT，不是生产默认值；存在未退还质押时禁止更改规则。

`C2cMerchantController` 校验交易登录身份；`C2cMerchantBonds` 持有商家质押状态，创建固定原资产、原金额的资金意图；`C2cFunds` 继续交给已有结算逻辑和 Core 执行。只有持久意图得到真实提交结果才从 RESERVING 变为 LOCKED，之后才能审核通过及上架广告。

退出要求关闭所有广告，结清订单、申诉和在途资金；风控停用的商家不能自行退押。退款固定原用户、原币种及原额，收到真实 Core 回执后才显示 RETURNED。质押和订单请求在发送前保存原请求号；响应丢失先查询原回执，显式重试沿用原身份。查询证明旧请求已存在后才清理客户端恢复标识，允许后续新的商家周期。Gateway 重启仍续办原资金意图和 transferId，不产生第二笔扣款。

`C2cProfiles.me().escrow` 已计入实际质押；存在在途资金时不伪造确定余额。内部托管与手续费账户均经 realtime 查询；冷启动会请求两个账户的查询视图，未就绪显示等待状态，不能将不可用误当余额 0。此处是 C2C 托管汇总，不代表全站资产估值已合并 C2C 资产。

## 验证范围与限制

实测覆盖双方广告、双向成交、手续费净额、原收款快照、取消、真实付款窗口到期退款、已付款订单不超时退款、两人审批申诉退款/放币、关闭广告后存量订单、Core 暂停及 Gateway 意外退出后的原请求恢复、商家质押与退押，以及停用商家禁止新交易但可履行原已付款订单。

浏览器使用真实交易登录身份，验证桌面与 390px 页面、原订单会话、外人拒绝访问以及聊天/行情帧来自同一条 `/ws/v1`。Flutter 在 320px 和 390px 运行真实 HTTP/Core widget 场景，验证丢失响应恢复仅一次下单 POST，以及商家质押/原额退押。并非真机安装或真实银行付款。已有聊天/R2 集成记录见 `docs/c2c-chat.md`；本轮附件使用隔离本地存储，没有重复执行真实 R2 上传。

后端定向测试合并同名用例后 102 项通过、3 项条件跳过；Web 324 项通过；管理端 16 项通过；Flutter 398 项通过、11 项条件跳过，另外显式本地实栈 widget 2 项通过。三端均完成各自静态检查，Web 和后台完成构建。后端在干净基线加本次 C2C 改动的独立目录使用 Corretto HotSpot JDK 27 构建，未纳入工作区其他算法单改动。

本轮不发布远端服务器、不安装 APK，不验证其他五条产品线的实栈或外部价格源。最终资金、终态和清理事实以 JSON 记录为准。
